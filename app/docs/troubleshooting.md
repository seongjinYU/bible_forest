```md

- **영역**: FE / BE
- **심각도**: 🔴 치명(서비스 중단·데이터 손상) / 🟡 주요(일부 기능 오작동) / 🟢 경미(UX 불편)

- **해결**: 어떻게 고쳤는지 (커밋/PR 링크 가능하면 첨부)
- **재발 방지**: 같은 문제를 막기 위해 추가한 장치(테스트, 모니터링, 코드 리뷰 체크포인트 등)
```

## FE (Frontend)

### [2026-07-08] `/forests` 페이지에서 React key 경고가 사라지지 않음

- **영역**: FE
- **심각도**: 🟢 경미(콘솔 경고, 기능 영향 없음)
- **증상**: `/forests` 페이지에서 "Each child in a list should have a unique key prop" 경고가 계속 발생. `ForestsRankingList`가 지목됐지만 이미 `.map()`에 `key={team.id}`가 존재해 원인을 특정하지 못한 채 한동안 헤맴.
- **원인**: `ForestsRankingList.tsx`가 최상위를 `<>`(Fragment)로 반환하면서 `{header}`를 형제 노드로 나열하고 있었음. `.map()`의 key 문제가 아니라, **최상위 반환 형태 자체**가 원인 — Fragment 밑에 나열된 형제 요소 중 리스트가 아닌 `header`에는 key가 없어서 발생.
- **해결**: 최상위 반환을 `<>`에서 `<div>`로 변경하고, `header`를 `<div key="ranking-header">{header}</div>`로 감쌈. (커밋: `29bdeea`, `549fc82` 계열)
- **재발 방지**: 별도 테스트는 추가하지 않음(렌더링 경고는 스냅샷/시각 검증으로 확인하는 영역). 대신 `ForestsRankingList`에서 실제 정렬 로직은 이후 `team-stats.ts`로 분리해 유닛 테스트(`team-stats.test.ts`)로 고정함.
- **회고**: `.map()`의 key만 보고 "이미 있는데 왜 나지"라고 판단해 오래 헤맸다. React key 경고는 **map 안이 아니라 형제 목록 전체**를 봐야 한다는 교훈 — 사용자가 제공한 정확한 에러 오버레이 스크린샷(`page.tsx:132` 지목)이 결정적 단서였음.

### [2026-08-11] S등급 획득 이펙트 재생 후 카드가 영원히 안 뜸

- **영역**: FE
- **심각도**: 🟡 주요(아이템 획득 다이얼로그 자체가 멈춤)

- **회고**: 애니메이션 종료 조건을 "파티클 배열이 비었는가"처럼 물리 시뮬레이션에 의존시키면, 파라미터 하나(소멸 속도)가 UI 흐름 자체를 막을 수 있다. 타임아웃 기반 안전장치(예: N초 후 강제 종료)를 같이 두는 게 안전했을 것.

### [2026-08-25] 이모지로 시작하는 닉네임의 프로필 아바타가 깨진 문자로 표시됨

- **영역**: FE
- **심각도**: 🟢 경미(UX 불편, 기능 장애 아님)
- **증상**: 닉네임이 이모지로 시작하는 유저(국기, 스킨톤 변형, ZWJ 결합 이모지 등)의 참여자 아바타에 물음표 박스 또는 깨진 문자가 표시됨.
- **원인**: `ParticipantAvatars.tsx`, `ParticipantsList.tsx`에서 `p.nickname[0]`으로 첫 글자를 추출했는데, JS 문자열 인덱싱은 UTF-16 코드 유닛 1개만 잘라낸다. 국기(지역표시문자 2개), 스킨톤 변형(베이스+수정자), ZWJ 결합 이모지는 모두 여러 코드 유닛으로 구성되어 있어 `[0]`이 서로게이트 페어의 절반만 잘라냄.
- **해결**: `src/lib/avatarInitial.ts`에 `getAvatarInitial()` 유틸 신규 작성. `Intl.Segmenter`로 grapheme(사용자가 인지하는 글자 단위) 기준으로 첫 글자를 추출하고, `\p{Extended_Pictographic}` 유니코드 속성으로 이모지 여부를 판별해 이모지면 빈 문자열을 반환(색상 배경만 남고 글자 없음). (커밋: `31fae6d`)
- **재발 방지**: `avatarInitial.test.ts`에 한글/영문/단순 이모지/스킨톤/ZWJ 가족 이모지/국기 이모지 케이스를 테스트로 고정.
- **회고**: 문자열을 다룰 때 `str[0]`, `str.charAt(0)`, `str.slice(0,1)` 모두 코드 유닛 단위라 이모지에 취약하다는 걸 놓치기 쉽다. 사용자 입력을 다루는 UI 표시 로직에서는 항상 grapheme 단위(`Intl.Segmenter` 또는 `Array.from`)를 우선 고려해야 한다.

### [운영 프로세스] Supabase 운영 DB에 검증용 테스트 계정을 반복 생성한 사고

- **영역**: BE(운영 데이터 안전)
- **심각도**: 🔴 치명(실제 운영 DB 오염 가능성)
- **증상**: 기능 검증을 위해 로컬 dev 서버(`npm run dev`)를 띄우고 Playwright로 회원가입 API를 반복 호출했는데, `.env.local`이 별도 개발용 DB가 아니라 **실제 운영 Supabase 프로젝트**를 가리키고 있어 검증용 계정("검증계정", "포레스트검증", "리딩검증" 등)이 실사용자 데이터와 같은 테이블에 계속 쌓임. 한 차례 사용자에게 "함부로 계정 생성하지 말라"는 지적을 받은 뒤에도 같은 실수를 반복함.
- **원인**: dev/prod Supabase 프로젝트 분리가 되어 있지 않은 상태에서, 검증 작업 전 현재 연결된 DB가 운영 DB인지 확인하는 절차가 없었음.
- **해결**: 닉네임 패턴("OO검증숫자" 형태로 실명 유저와 명확히 구분됨)으로 전수 조회 후, 나무/진행기록이 전혀 없는 것을 확인하고 32개 테스트 계정을 일괄 삭제(`bible_progress`/`trees`는 `on delete cascade`로 함께 정리됨). 삭제 전 반드시 SELECT로 대상 확인 → 사용자 승인 → DELETE 순서로 진행.
- **재발 방지**: 앞으로 운영 DB에 데이터를 쓰는 검증(회원가입 등)은 사전에 반드시 사용자에게 확인받기로 함. dev/prod Supabase 프로젝트 분리(별도 프로젝트 생성 + `.env.local`은 dev 키, 배포 환경변수는 prod 키)가 근본 해결책으로 논의됐으나 아직 실행 전.
- **회고**: "로컬에서 실행하니 안전하다"는 가정이 틀렸다 — 로컬/운영을 가르는 것은 실행 위치가 아니라 **연결된 DB**다. 검증 작업을 시작하기 전 `.env.local`의 `NEXT_PUBLIC_SUPABASE_URL`이 가리키는 프로젝트가 운영인지 확인하는 걸 습관화해야 한다.
